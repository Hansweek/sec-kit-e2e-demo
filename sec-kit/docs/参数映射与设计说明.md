# 参数映射与设计说明 · sec-kit v2

> 面向对接方/交付工程师。说清楚三件事：**CI 侧取什么参数 → 怎么拼接 → 落到平台什么参数**；
> 以及 v2 各能力的接口依据与已实测行为（2026-10-12，CodeAI 5.0 / 源鉴SCA 4.13.0，sast.igovee.com）。

## 一、总体架构（分层与抽象）

```
┌─ CI 适配层（薄，无逻辑无密钥，只做"触发+变量翻译"）─┐
│  ci/github-actions/security-scan.yml   SAST/SCA 两个 job 并行 + report job 聚合 │
│  ci/yunxiao/yunxiao-security-step.sh   云效自定义Shell一步编排(SAST+SCA+通知)   │
│  (GitLab/Jenkins 等新平台: 照抄一层翻译即可)                                    │
└──────────────────────────┬───────────────────────────┘
                           │ 统一环境变量契约(下表)
┌─ 核心脚本层（平台无关，bin/）────────────────────────┐
│  codeai-incremental-scan.sh  SAST: 增量感知+项目纳管v2+详情报告+全缺陷跟踪导出   │
│  sca-scan.sh                 SCA: 项目纳管v2+依赖/制品扫描+红线+报告            │
│  sca-sbom.sh                 SBOM(SPDX/CycloneDX)+VEX(CSAF) 专用导出           │
│  sec-notify.sh               聚合通知(钉钉加签/企微/飞书)                       │
│  codeai-scan.sh              SAST全量兜底(故障时替换用)                         │
└──────────────────────────┬───────────────────────────┘
                           │ OpenAPI (SAST: Sast-Token / SCA: OpenApiUserToken+ProjectToken)
                    ┌──────┴──────┐
                    │ CodeAI 平台  │  │ 源鉴SCA 平台 │
                    └─────────────┘  └──────────────┘
```

**换 CI 平台只写适配层**：把新平台的内置变量翻译成统一契约变量即可，核心脚本零修改。

## 二、CI 参数 → 统一契约变量 → 平台参数 全映射

### 2.1 仓库身份（应用名/项目名拼接规则）

| 平台取值 | GitHub Actions | 云效 Flow | 拼接规则 | 落到平台参数 |
|---|---|---|---|---|
| 仓库名 | `github.event.repository.name` | git remote 或 `CI_REPOSITORY_NAME` | 原样 | SAST `projectName` / SCA `name`（项目名=仓库名） |
| 分支名 | `github.head_ref`(PR) 或 `github.ref_name`(push) | `CI_COMMIT_REF_NAME` | `/`与空格转 `_` | 应用名后缀 |
| **应用名** | `仓库名-分支名`（`tr '/ ' '__'`） | 同左 | `e2e-demo-app-main` | SAST `saveOrAgainTask.addTaskJson.appName`；SCA `package/task/add2.taskName` |
| 提交SHA | `github.sha` | `CI_COMMIT_ID` | 原样（SAST 作 gitHash 回写增量基线） | SAST 表单字段 `gitHash` |
| 触发类型 | `github.event_name`/`ref_type` | `CI_COMMIT_REF_NAME` 前缀 `refs/tags/` | tag→全量；schedule/手动强制→全量；其余→增量 | SAST `incrementSwitch: "1"/"0"/不带` |
| 构建人 | `github.actor` | `CI_COMMITTER_NAME` | 原样 | 通知卡片展示 |
| 构建链接 | `server_url/repo/actions/runs/run_id` | `流水线名 #CI_BUILD_NUMBER` | 拼URL/文案 | 通知卡片链接 |

### 2.2 项目自动纳管 v2（SAST · CodeAI）

| CI 配置 | 统一变量 | 解析过程 | 平台参数（接口） |
|---|---|---|---|
| vars.SAST_USERNAME | `SAST_USERNAME` | `GET open-api/system/user/page?username=` → `{userId, departmentId}` | `project/add` 的 `pmId`=userId（**项目经理=令牌归属人**）、`departmentId`=归属人部门（**项目归属部门**） |
| （协作人自动拉取） | `SAST_PROJECT_MEMBERS` | GitHub: `GET /repos/{o}/{r}/collaborators`(GITHUB_TOKEN→PAT→手工变量三级降级) → login 列表 → 逐个 `user/page` 精确匹配 userId；不匹配的记警告 | `project/add` 的 `userIds=[...]`（**仓库协作人→项目成员**） |
| vars.SAST_PROJECT_NAME（缺省=仓库名） | `SAST_PROJECT_NAME` | `GET open-api/project/page` 翻页找同名 → 无则创建 | `projectName` |
| vars.SAST_PROJECT_ID | `SAST_PROJECT_ID` | 数字直用（优先级最高） | `saveOrAgainTask.addTaskJson.projectId` |
| — | `SAST_PROJECT_AUTO_CREATE=0` | 关闭自动创建（默认1） | — |

已实测行为（2026-10-12）：
- CodeAI 5.0 的 `project/add` **必须带 pmId+departmentId**（仅项目名报 400）；`userIds` 创建时生效，OpenAPI 无后续成员更新接口（加人走平台 UI）。
- 归入项目的应用**必须按项目维度查**：`GET open-api/app/info/{projectId}?appName=`（旧 `app/task/info?name=` 对项目内应用返回空）——脚本已按"项目优先、旧接口兜底"实现。
- 增量链路：应用复用 → `GET open-api/app/git/hash/{appId}` 取基线 → `git diff <hash> HEAD --name-only` 生成 diff 清单 → `saveOrAgainTask` 带 `incrementSwitch:"1"`+`diff` 文件 → 平台按变更文件增量检测并回写新基线。

### 2.3 项目自动纳管 v2（SCA · 源鉴）

| CI 配置 | 统一变量 | 解析过程 | 平台参数（接口 :30002/openapi/v1） |
|---|---|---|---|
| vars.SCA_USERNAME（缺省继承 SAST_USERNAME，云效侧同） | `SCA_USERNAME` | `POST user/list {nameList:[u]}` → `{userId, departmentId}` | `project/create` 的 `managerList=[userId]`（**项目经理=令牌归属人**）、`departmentId`（**归属部门**） |
| （协作人） | `SCA_PROJECT_MEMBERS` | 同 2.2 解析为 userId 列表 | `memberList=[...]`（**仓库协作人→项目成员**） |
| vars.SCA_PROJECT_NAME（缺省=仓库名） | `SCA_PROJECT_NAME` | `POST project/list {nameOrDescription}` 精确同名 → 无则 create | `name` |
| `SCA_PROJECT_SYNC_MEMBERS=1`（可选） | 同名 | 项目已存在时 `POST project/edit` 幂等同步 managerList/memberList | `projectId+managerList+memberList` |

| 统一变量 | 默认 | 平台参数 |

| `AUTO_LANGUAGE=1` | 自动识别 | `addTaskJson.autoLanguage` |

### 2.5 扫描任务参数（SCA）

| 统一变量 | 默认 | 平台参数（:30002/openapi/v1） |
|---|---|---|
| `DEPS_GATE/ARTIFACT_GATE` | 0/1 | 红线判定 `POST /sca/api-v1/engine/rule/handle/rule`（sceneCode=1, projectId, taskId） |
| `SCAN_PATTERNS` | — | 制品扫描文件收集正则 |
| `AUTO_SBOM=1` | 开 | 扫描完成后自动调 `sca-sbom.sh` |

| `REPORT_NAME/EXPORT_TYPE` | 应用名-report / 5(Excel) | `POST asset/report/application/sca/generate`（报告中心 type=5） |

### 2.6 通知（自搓 webhook，推荐方式）

| CI 配置 | 统一变量 | 行为 |
|---|---|---|
| secrets.NOTIFY_WEBHOOK | `NOTIFY_WEBHOOK` | 流水线**最后一步**调 `sec-notify.sh`，读 sec-results/*.json 聚合成一张紧凑卡片：引用块三行核心数据（缺陷四色/漏洞四色/组件与许可证基础数据）+ 各检测分段导航链接；门禁未启用=「📋 检出摘要」中性结论（不出现"通过"字样）；增量扫描显式标注口径；支持加签/超长截断/DRY_RUN调试 |
| secrets.NOTIFY_SECRET | `NOTIFY_SECRET` | 钉钉**加签**模式自动计算 timestamp+sign（HMAC-SHA256），比平台侧逐应用配置更省事、且 SAST/SCA 消息合一 |
| vars.DINGTALK_AT | `NOTIFY_AT` | @指定手机号（逗号分隔） |
| vars.NOTIFY_TYPE | `NOTIFY_TYPE` | dingtalk / wecom / feishu |

> 平台侧原生通知（CodeAI 任务通知/SCA 消息中心）仍可并行启用，但需要逐应用配置且格式固定；
> 脚本内 webhook 聚合方案一次配置全仓库生效，是 v2 的默认推荐。

## 四、平台行为备注（实测结论，配置前必读）

1. **VEX 内容语义**：VEX 是"处置结论声明"。应用漏洞未做审计时，平台导出的 CSAF `vulnerabilities` 为空数组属正常语义；随平台侧漏洞审计推进，VEX 内容自动丰富。固件/组件漏洞明细以 `sca-result.json 的 resultUrl` 与 Excel 报告为准。
2. **SAST 应用复用**：应用归入项目后只能按项目维度检索（v2 已适配）；跨项目同名应用互不影响。
3. **SCA 项目成员**：`project/edit` 支持成员/负责人后续同步（幂等），SAST 暂仅创建时生效。
4. **VEX-CycloneDX(format=1)** 在 4.13.0 生成卡死（status 长期=2），v2 默认 `vex` 仅产 CSAF；待平台修复后可在 `SBOM_TYPES` 加回。
5. **协作人→成员映射前提**：平台存在与 git 用户名**同名**的账号（Govee 两平台的账号体系与 GitHub login 同名，如 xin.wang）。未匹配的协作人会在流水线日志中警告，需在平台建号后重跑（SCA）或 UI 加人（SAST）。
6. **令牌归属人**：OpenAPI 无 whoami 接口，故以 `SAST_USERNAME`/`SCA_USERNAME` 变量显式声明（一次配置）；未配置时回退 SAST_PROJECT_PM_ID/DEPT_ID 显式配置或平台默认管理员/默认部门。


## 五、命名、SKU 分层与对比逻辑（v3 定稿，2026-10-12，对齐 9/24 会议决议）

> **设计定位（重要）**：本节是一套**约定与映射**，不是强制的目录结构。APP/后端/微服务仓库**不需要任何额外配置**，
> 默认命名（项目=仓库名、应用=仓库-分支）即可完整工作；SKU/业务线是**可选增强**，
> 主要服务于嵌入式固件场景（9/24 会议确认的"品线分支→SKU 分支"分层），后端仓库不启用时零影响。

### 5.1 命名模型（平台三层数据结构 × Govee 业务分层）

```
平台项目管理(project)      平台应用(application)           平台任务/版本(task/version)
──────────────────       ────────────────────────       ──────────────────────────
项目名 = 仓库名      ←—   应用名 = 仓库名-分支名      ←—   每次扫描一条任务
(SCA: 描述带业务标识)      (制品扫描 = 仓库名-分支名-artifact)  CodeAI任务含gitHash;
                                                              SCA版本=自增"N#时间戳"
```

**SKU 分层如何落入这套模型**（9/24 会议确认的客户分支策略）：

```
仓库 repo-x (品线仓库, 如 rgbic 灯带固件)
├── main            品线主干(通用品线)        → 应用 repo-x-main        [品线时间线]
├── sku/H6161       SKU分支(具体产品,从品线切出) → 应用 repo-x-sku_H6161  [该SKU时间线]
└── sku/H6199       另一SKU                  → 应用 repo-x-sku_H6199
```

- **每个 SKU 分支 = 平台上独立应用**，版本自增形成该 SKU 的扫描历史——天然对应"一个产品一条成分档案"（CRA 要求按产品出 SBOM，这就是产品↔SBOM 的映射）
- **漏洞修复回主干**（SKU 分支修复验证 → 合并品线分支）后，品线应用与各 SKU 应用的版本对比即可回答"修复是否覆盖所有产品"——平台版本对比功能直接支撑 9/24 会议的修复闭环语义
- **SKU↔应用的反查**：会议确认"按仓库名+报告内容识别 SKU 编号→反推关联回平台"。v3 实现为**流水线自动解析**：分支名符合 `sku/<SKU>` 或 `sku-<SKU>` 模式时自动提取；也可在 CI 变量显式指定 `SKU_ID`/`BIZ_LINE`（品线/产品线命名不受限，客户自定义）。解析结果自动写入：
  - SCA 项目描述 + SCA 应用描述（`sec=kit;repo=…;branch=…;biz=…;sku=…` 格式化串，平台内可检索）
  - CodeAI 项目描述
  - 通知卡片（标题与元信息行）
  - 结果 JSON（`sku`/`biz` 字段，供 VMS/ASOC 同步时做资产关联）

### 5.1.1 应用名与版本号的关键实测结论

| 结论 | 依据（2026-10-12 实测） |
|---|---|
| SCA 应用名取自**上传包 originName**，不是 taskName | originName=`x.tar.gz` → 应用名显示 `x_.tar.gz`（污染）；originName=干净名 → 应用名干净。v3 起上传 originName=应用名本体 |
| SCA 版本号 `N#时间戳` 为平台自增，不可自定义 | add2 接口无版本参数；commit 追溯走任务记录+通知卡片+结果JSON |
| SCA add2 支持 `description` 参数 | 实测写入应用描述——SKU 标识的落点 |
| CodeAI project/add 支持 `description` | 实测写入项目详情——业务标识的落点 |
| 同分支重复扫描自动归并同应用 | 版本对比的基线；跨分支对比=跨应用不适用（用两张结果页并读） |

### 5.2 版本对比的正确姿势（写进对客培训口径）

- **看分支演进**：平台 → 项目管理 → 仓库名项目 → 应用 `repo-main` → 版本列表（N#时间戳）→ 任选两版对比（新增/消失组件、漏洞变化）
- **对应到代码**：版本号只有平台语义，commit 对应关系看两条线索——①流水线的扫描记录（卡片/JSON 带 commit 短 SHA + 流水线链接）；②CodeAI 侧任务列表直接显示 gitHash
- **跨分支对比**：属于"跨应用"（repo-main vs repo-dev），平台版本对比不适用；用两张卡片/两个结果页并读

### 5.3 角色、成员与权限生命周期（平台能力边界内的完整流程）

**CodeAI（角色：项目经理 + 项目成员[用户/部门]）**

| 时机 | 动作 | 通道 |
|---|---|---|
| 项目创建时（自动） | 项目经理=令牌归属人；归属部门=归属人部门；项目成员=仓库协作人（userIds）+ 归属部门（departmentIds，**实测接口接受**；对应平台 UI"添加项目成员"里的部门选择，部门作为成员单位授权） | OpenAPI project/add |
| 项目创建后（日常） | 加人/换项目经理：平台 UI → 项目管理 → 该项目 → 添加项目成员 / 变更项目经理（**OpenAPI 无成员更新接口，这是平台边界**） | UI 操作（PM 或管理员） |
| 令牌归属人离职 | 管理员在平台 UI 变更项目经理；更新 CI 变量 SAST_USERNAME 与新令牌 | UI + CI 配置 |

**SCA（角色：创建人 / 负责人 managerList / 成员 memberList，带权限分级）**

| 时机 | 动作 | 通道 |
|---|---|---|
| 项目创建时（自动） | managerList=令牌归属人；departmentId=归属部门；memberList=仓库协作人 | OpenAPI project/create |
| 项目已存在时（可选自动） | 流水线变量 `SCA_PROJECT_SYNC_MEMBERS=1` → 每次 provision 调 project/edit 幂等同步 managerList/memberList（权限不足自动跳过不阻断） | OpenAPI project/edit |
| 日常加人 | 同上 edit 同步，或平台 UI 项目设置 → 成员管理 | 两者皆可 |

**推荐治理节奏**（写进客户安全部门流程）：
1. GitHub 侧保证"平台账号名 = Git 用户名"（入职建号同步），协作人映射全自动；
2. 每季度核对一次项目成员清单（平台项目成员 vs 仓库 collaborators）；
3. 部门维度授权用于"整个部门都要看"的场景（如数字平台-安全部门巡检所有项目）；
4. 离职/转岗：先平台移除，再仓库移除——顺序反了会有窗口期残留权限。
